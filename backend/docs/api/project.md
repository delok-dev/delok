# Project API

All project operations are mounted under an explicit **organization boundary**:

- **`/api/organizations/:organizationSlug/projects`** — list / create within an org
- **`/api/organizations/:organizationSlug/projects/:projectSlug`** — get / update / delete a project within an org
- **`/api/organizations/:organizationSlug/projects/by-id/:projectId`** — internal helper lookup by database ID

All endpoints require session authentication.

There is **no** standalone project route (e.g. `/api/project/:id`). Project access is always scoped to the organization represented by the request URL. See [Resource Boundary](#resource-boundary) below.

---

## Identifier strategy

Projects are addressed by **slug** in all public CRUD routes. The slug format is `normalized-name-<12-hex-suffix>` (generated by `utils/project-slug.ts`). The database CUID (`projectId`) is used only for the internal `by-id` lookup helper and for log-ingestion routing — never for public project CRUD.

On project update (`PATCH`), the slug prefix is regenerated while the 12-hex suffix is preserved (`regenerateProjectSlugPrefix` in `project.repository.ts`). The response reflects the new slug.

## `GET /api/organizations/:organizationSlug/projects` — List Projects in Org

Return all projects belonging to a specific organization.

### Request

- Method: `GET`
- URL: `/api/organizations/:organizationSlug/projects`
- Params: `organizationSlug` (URL slug)
- Query: None
- Body: None

### Authorization

`ensureOrganizationMember(organizationSlug, userId)` — user must be MEMBER or OWNER. The service resolves the slug to the organization, then lists projects by that organization's id.

### Response: `200 OK`

```json
{
  "success": true,
  "data": [
    {
      "id": "cl...",
      "slug": "my-web-app-a1b2c3d4e5f6",
      "name": "My Web App",
      "organizationId": "cl...",
      "logCount": 42,
      "createdAt": "2026-07-15T08:00:00.000Z",
      "updatedAt": "2026-07-15T08:00:00.000Z"
    }
  ]
}
```

Service: `getAllProjectsService(organizationSlug, userId)` → resolves slug → repo `findAllProjects(organizationId)` (findMany by org FK).

## `POST /api/organizations/:organizationSlug/projects` — Create Project

Create a new project inside an organization. Requires org OWNER role.

### Request

- Method: `POST`
- URL: `/api/organizations/:organizationSlug/projects`
- Params: `organizationSlug`
- Body (validated by `projectSchema`):

```json
{
  "name": "My Web App"
}
```

| Field | Zod rule |
| ------ | ------------------------------------- |
| `name` | Required string, trimmed, 3–100 chars; case-insensitive unique per organization (DB index `project_organizationId_lower_name_idx` on `lower(name)`, migration `20260819120000`) — duplicate (case-insensitive) returns `409` via `P2002` |

### Authorization

`ensureOrganizationOwner(organizationSlug, userId)` — only org owners can create projects. The service resolves the slug to the organization id before creating the project row.

### Response: `201 Created`

```json
{
  "success": true,
  "data": {
    "id": "cl...",
    "slug": "my-web-app-a1b2c3d4e5f6",
    "name": "My Web App",
    "organizationId": "cl...",
    "createdAt": "2026-07-15T08:00:00.000Z",
    "updatedAt": "2026-07-15T08:00:00.000Z"
  }
}
```

Service: `createProjectService(name, userId, organizationSlug)` → resolves slug → repo `createProject(name, organizationId)`.

### Error Responses

| Scenario | Status | Message |
| ---------------------------------- | ------ | --------------------- |
| Member (not Owner) tries to create | 403 | `organization.access_denied` |
| Name < 3 or > 100 | 400 | Zod issues array |
| Name already exists (case-insensitive) | 409 | `PROJECT_NAME_ALREADY_EXISTS` |

## `GET /api/organizations/:organizationSlug/projects/:projectSlug` — Get Project

Return a single project's details, scoped to the organization.

### Request

- Method: `GET`
- URL: `/api/organizations/:organizationSlug/projects/:projectSlug`
- Params: `organizationSlug`, `projectSlug`

### Authorization

Two checks, applied in order:

1. `ensureOrganizationMember(organizationSlug, userId)` — user must be MEMBER or OWNER of the organization in the URL.
2. `ensureProjectInOrganization(projectSlug, organization.id)` — the project must belong to that organization.

The project's organization boundary is encoded directly in the repository query (`findProjectBySlugAndOrganization(projectSlug, organizationId)`), so a project that belongs to a different organization is never returned even if the user is a member of that other organization too.

### Response: `200 OK`

```json
{
  "success": true,
  "data": {
    "id": "cl...",
    "slug": "my-web-app-a1b2c3d4e5f6",
    "name": "My Web App",
    "organizationId": "cl...",
    "createdAt": "2026-07-15T08:00:00.000Z",
    "updatedAt": "2026-07-15T08:00:00.000Z"
  }
}
```

Service: `getProjectBySlugService(organizationSlug, projectSlug, userId)`.

## `PATCH /api/organizations/:organizationSlug/projects/:projectSlug` — Update Project

Change a project's name. Requires parent org OWNER role (not just MEMBER), and the project must belong to that organization.

### Request

- Method: `PATCH`
- URL: `/api/organizations/:organizationSlug/projects/:projectSlug`
- Params: `organizationSlug`, `projectSlug`
- Body:

```json
{
  "name": "Renamed Project"
}
```

Same Zod rules as create (trimmed, 3–100 chars).

### Authorization

1. `ensureOrganizationOwner(organizationSlug, userId)` — 403 if not an owner.
2. `ensureProjectInOrganization(projectSlug, member.organizationId)` — 404 if the project does not belong to that organization.

### Response: `200 OK`

```json
{
  "success": true,
  "data": {
    "id": "cl...",
    "slug": "renamed-project-a1b2c3d4e5f6",
    "name": "Renamed Project",
    "organizationId": "cl...",
    "createdAt": "2026-07-15T08:00:00.000Z",
    "updatedAt": "2026-07-15T08:15:00.000Z"
  }
}
```

> **Note:** The slug prefix is regenerated on update while the 12-hex suffix is preserved. The response reflects the new slug.

Service: `updateProjectService(organizationSlug, projectSlug, userId, name)` → resolves slug → repo `updateProject(projectId, name)`.

## `DELETE /api/organizations/:organizationSlug/projects/:projectSlug` — Delete Project

Delete a project and **cascade** all ApiKeys and LogEvents. Requires org OWNER role, and the project must belong to that organization.

### Request

- Method: `DELETE`
- URL: `/api/organizations/:organizationSlug/projects/:projectSlug`
- Params: `organizationSlug`, `projectSlug`

### Authorization

1. `ensureOrganizationOwner(organizationSlug, userId)` — 403 if not an owner.
2. `ensureProjectInOrganization(projectSlug, member.organizationId)` — 404 if the project does not belong to that organization.

### Cascade Impact (DB-level)

- All `ApiKey` rows for this project deleted
- All `LogEvent` rows for this project deleted

### Response: `200 OK`

```json
{
  "success": true,
  "data": {
    "id": "cl...",
    "slug": "deleted-project-a1b2c3d4e5f6",
    "name": "Deleted Project",
    "organizationId": "cl...",
    "createdAt": "2026-07-15T08:00:00.000Z",
    "updatedAt": "2026-07-15T08:00:00.000Z"
  }
}
```

Service: `deleteProjectService(organizationSlug, projectSlug, userId)` → resolves slug → repo `deleteProject(projectId)`.

### Error Responses

| Scenario | Status | Message |
| ------------------------------------- | ------ | --------------------------- |
| No session | 401 | `unauthorized` |
| User is not owner of the URL organization | 403 | `organization.owner_access_denied` |
| Project does not exist in that organization | 404 | `project.not_found` |

## Internal: `GET /api/organizations/:organizationSlug/projects/by-id/:projectId` — Get Project By ID

Internal helper that resolves a project by its database CUID. Used by frontend/backend flows that already have the numeric ID. Authorization is the same as the slug-based GET.

### Request

- Method: `GET`
- URL: `/api/organizations/:organizationSlug/projects/by-id/:projectId`
- Params: `organizationSlug`, `projectId` (project CUID)

### Authorization

Same two-check pattern as the slug-based GET (`ensureOrganizationMember` + `ensureProjectInOrganization`).

### Response: `200 OK`

Same shape as the slug-based GET response (includes `slug`).

## Resource Boundary

Project CRUD is deliberately organization-scoped. The backend validates **both**:

1. The authenticated user has the required access to the **organization represented by the URL** (member for read, owner for write).
2. The requested project actually belongs to **that organization** (`project.organizationId === organization.id`).

### Why `projectId` alone is not sufficient

A `projectId` (CUID) does not carry organization context. Given only a project ID, a request could authorize a project based on its *actual* parent organization while the frontend URL refers to a *different* organization, causing a resource-boundary mismatch.

The organization in the URL must be the source of truth.

### Wrong-organization behavior (non-leaking)

When a request targets a project that does not belong to the organization in the URL, the backend returns **404 `project.not_found`**. It does **not** reveal that the project exists under a different organization. This holds even when the user is a member of both organizations.

### Authorization order

```
Authenticated user
        ↓
Resolve organization by slug
        ↓
Verify user membership / ownership
        ↓
Resolve project inside that organization
        ↓
Verify project belongs to organization  (ensureProjectInOrganization)
        ↓
Perform operation
```

### Why this matters (examples)

Given: user is a member of `delok-v2` and `test5`; project `P` belongs to `delok-v2`.

| Request | Result |
| -------------------------------- | ------ |
| `GET /api/organizations/delok-v2/projects/P` | 200 |
| `GET /api/organizations/test5/projects/P` | 404 |
| `PATCH /api/organizations/test5/projects/P` (even as owner) | 404 |
| `DELETE /api/organizations/test5/projects/P` (even as owner) | 404 |
| `PATCH /api/organizations/delok-v2/projects/P` (owner) | 200 |

## Authorization helpers

| Helper | Signature | Purpose |
| ------ | --------- | ------- |
| `ensureOrganizationMember` | `(slug, userId)` | 403 if user is not a member/owner |
| `ensureOrganizationOwner` | `(slug, userId)` | 403 if user is not an owner |
| `ensureProjectInOrganization` | `(projectSlug, organizationId)` | 404 if project does not exist in the org |
| `ensureProjectMemberBySlug` | `(organizationSlug, projectSlug, userId)` | Primary path for GET/PATCH/DELETE project by slug |
| `ensureProjectManagementAccess` | `(projectId, userId)` | Owner-only check for API key management |

`ensureProjectInOrganization` uses `findProjectBySlugAndOrganization(projectSlug, organizationId)` for slug-based routes, and `findProjectByIdAndOrganization(projectId, organizationId)` for the `by-id` path. Both encode the boundary in the query itself — they never fetch a project belonging to another organization.

## Mounting in App

From `app.ts`:

```typescript
app.use(
  "/api/organizations/:organizationSlug/projects",
  organizationProjectRoute,
);
```

The router uses `{ mergeParams: true }` so controllers can access `req.params.organizationSlug` and `req.params.projectSlug`. The internal `by-id` route is mounted inside the same router at `/by-id/:projectId`.
